## Why this matters

`file-extension-icon-js@1.1.6` is a runtime dependency used in exactly 3 files,
only to render material-style file/folder icons. Its `package.json` declares
`react-scripts@4.0.3`, `react@^17.0.1`, `react-dom@^17.0.1`,
`@testing-library/*`, and `web-vitals` as hard **dependencies** (verified in
`bun.lock:2548`). That drags webpack 4, jest 26, eslint 7, an ancient
`immer@8.0.1`, `webpack-dev-server@3`, and dozens of known-vulnerable
transitive packages into `node_modules` on every install. None of it ships in
the app bundle (Vite tree-shakes), but it bloats installs, slows CI, pollutes
every `bun audit` run with noise, and is a real supply-chain surface (the
package was last published years ago by a single author). Replacing it
eliminates an entire class of audit findings in one small change.

## Current state

The package exposes `getMaterialFileIcon(name)` and
`getMaterialFolderIcon(name, open?)`, both returning **base64 `data:image/svg+xml` URI strings**
(self-contained, no network). Usage sites (all verified at commit `2818226c`):

- `src/features/panel/message-components/tool-call.tsx:1` — imports `getMaterialFileIcon`; used at lines 153, 162, 287, 299 as `<img src={getMaterialFileIcon(...)} alt="" className="size-4 shrink-0" />` (and `size-3.5` variants).
- `src/features/editor/index.tsx:2` — imports `getMaterialFileIcon`; used at line 149 in a breadcrumb: `<img src={getMaterialFileIcon(segment)} ... className="mr-1 size-4 shrink-0" />`.
- `src/features/inspector/panel/git/shared.ts:4-6` — imports both functions; wraps them in memo caches:

```ts

fileIconCache.set(name, icon);
...
const icon = getMaterialFolderIcon(name, open || undefined);

```

- `package.json:53` — `"file-extension-icon-js": "^1.1.6"` under `dependencies`.

## Steps

### Step 1: Vet the replacement package

Candidate: `vscode-material-icons` (ships the material-icon-theme SVGs plus
`getIconForFile` / `getIconForFolder` / `getIconForOpenFolder` name-mapping
helpers; assets are static SVG files you serve from your own bundle).
Fallback candidate: `material-file-icons` (zero-dep, returns SVG strings).

Run: `bun info vscode-material-icons dependencies` and
`bun info vscode-material-icons` (check version recency and that
`dependencies` is empty or near-empty with no framework deps).

**Verify**: the chosen package has NO `react`, `react-scripts`, webpack, or
testing-library entries in its `dependencies`. If both candidates fail this
test, STOP (see STOP conditions) — do not pick a third package on your own.

### Step 2: Create `src/lib/file-icons.ts`

A single module exporting the same call shape the three usage sites need:

```ts
export function getFileIconUrl(fileName: string): string { ... }
export function getFolderIconUrl(folderName: string, open?: boolean): string { ... }
```

Implementation notes for `vscode-material-icons`: it maps names to icon file
names; import the SVG assets via Vite (e.g. `import.meta.glob` over the
package's `generated/icons/*.svg` with `{ as: "url", eager: false }` is NOT
needed — prefer the package's documented asset-path API and Vite `?url`
imports, or copy the needed behavior per its README). The function must return
a string usable directly as `<img src>`. Keep the module under 100 lines.

**Verify**: `bun run typecheck` → exit 0.

### Step 3: Add unit tests

Create `src/lib/file-icons.test.ts` (vitest, co-located, like other `src/lib`
tests). Cases:
- `getFileIconUrl("foo.ts")` returns a non-empty string ending in `.svg` or
  starting with `data:image/svg`.
- `getFileIconUrl("Makefile")` and `getFileIconUrl("unknown.zzz9")` both return
  a non-empty string (fallback icon — must not throw).
- `getFolderIconUrl("src")` and `getFolderIconUrl("src", true)` return
  non-empty strings, different from each other OR documented as identical.

**Verify**: `bun x vitest run src/lib/file-icons.test.ts` → all pass.

### Step 4: Swap the three usage sites

- `tool-call.tsx`: replace the line-1 import with
  `import { getFileIconUrl } from "@/lib/file-icons";` and rename the 4 call
  sites (lines ~153, 162, 287, 299).
- `editor/index.tsx`: same swap at line 2 and call site ~149.
- `inspector/panel/git/shared.ts`: swap both imports; the memo caches stay
  exactly as they are, only the inner calls change to
  `getFileIconUrl(name)` / `getFolderIconUrl(name, open || undefined)`.

**Verify**: `grep -rn "file-extension-icon-js" src/` → no matches.
`bun run typecheck` → exit 0. `bun run test:frontend` → all pass.

### Step 5: Remove the dependency

Remove `"file-extension-icon-js"` from `package.json` dependencies, add the
replacement package, run `bun install`.

**Verify**: `grep -c "file-extension-icon-js" bun.lock` → 0.
`bun run build` → exit 0.

### Step 6: Visual smoke check (best effort)

If a debug build is feasible in your environment, run `bun run dev` and confirm
file icons render in: a chat tool-call row, the editor breadcrumb, and the
inspector Git file list. If you cannot run the app, state that plainly in your
report — do not claim visual verification you didn't do.
